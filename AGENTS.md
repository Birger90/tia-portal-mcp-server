# Project overview

MCP server for Siemens TIA Portal V21. Exposes 11 tools in read-only, 30 in read-write (startup default), and the same 30 in full mode (the counts include the three S7-PLCSIM Advanced tools `plcsim_read`, `plcsim_write`, `plcsim_test`, the two S7-1500 Web API tools `plc_online_read`, `plc_online_write` and the two library tools `library_read`, `library_write`; `plc_tia_online` and `plc_station_upload` are the two writable Openness online tools). Read-write permits in-project edits, compile, simulation control, lifecycle, `plc_download` (to PLCSIM or real hardware) online changes of user-configured S7-1500 CPUs (`plc_online_write`), TIA Portal go online/offline (`plc_tia_online`), station upload (`plc_station_upload`) and project/global library work (`library_write`), with one confirmation prompt per actual lifecycle, download, online-write, online-connection or upload call and per `library_write` call that contains a global-library lifecycle item. Full runs those without server elicitation and adds no tools or operations; the TIA Portal (Openness) PLC run/stop was removed, and operating-mode changes exist only as `plc_online_write change_operating_mode` over the Web API. The installer defaults to read-only. Windows-only, requires TIA Portal V21 with Openness enabled. Content tools (content reads and writes, `compile_check`, and every lifecycle tool except `open_project`/`create_project`) act only on the bound project and fail closed with `binding_conflict` when unbound; only `bind_project` and `open_project` accept a public `projectPath`, and `get_project_status` takes no arguments.

## Two-process architecture (critical to understand)

The host (`TiaMcpServer`, net10.0) and the worker (`TiaMcpServer.OpennessWorker`, net48) are separate processes. Siemens Openness DLLs use .NET Framework remoting and **cannot run in a .NET 10 process** — this is why the split exists.

- Host communicates with worker via newline-delimited JSON over stdin/stdout
- The host builds the worker and copies it to `openness-worker/` subdirectory automatically
- The worker restarts automatically after crash or timeout
- A read or session selection without a verified binding that the worker has not answered after 25 s (`OpennessWorkerClient.PortalAccessNoticeDelay`, K37: TIA Portal's Openness access dialog after a new worker build) returns `worker_timeout` with `WorkerTransportFailureGuidance.PortalAccessPending`; the worker keeps the request and the transport serializes the next call behind it; writes and lifecycle are never returned early
- Worker request timeout is parsed once at startup from `--worker-timeout-minutes` or `TIA_MCP_WORKER_TIMEOUT_MINUTES` (CLI > environment > default), accepts whole minutes 5–60 with default/floor 5, applies to every request including `hello`, and is reported with its source by `doctor`.
- `ref/` contains compile-time Siemens stubs (`Siemens.Engineering.Base`, `.Step7` and `.WinCCUnified`) so CI can build without TIA Portal installed

**Do not try to run Openness code directly from the host process** — always go through the worker.

## Multiuser (inspection and local sessions)

`bind_project` retains default/null/explicit `bind` behavior and adds six explicit inspections:
`list_portals`, `list_server_connections`, `list_server_groups`, `list_server_projects`,
`list_local_sessions`, `get_lock_state`. Current counts are 11/30/30 (11/29/29 before `retrieve_project`, 10/27/27 before `library_read`/`library_write`, 10/25/25 before `plc_tia_online` and `plc_station_upload`, 9/23/23 before the Web API tools, 8/19/19 before `plc_download` and the PLCSIM tools); PR3 had 7/17/17. Discovery never adopts; inventory
uses persistent Portal-only attachment, never switches/adopts/opens a project. Selectors are exact
raw-key validated; root group requires `{isRoot:true,name:null}`. Verified foreign-PID refusal is
local/NotSent and preserves binding/cursors; genuine context/transport loss still invalidates.
Sessions cover `currentMachineCurrentUser`; locks are non-atomic observations. Typed inspection
is conditional inside the budgeted binding value (60,000/180,000 characters by default), not a new envelope.
Inspection adds no lifecycle elicitation/write audit or session mutation.
See [Multiuser reference](docs/SupportedOperations/MULTIUSER_OPERATIONS_SUMMARY.md).

Binding selects typed already-open local owners by observed `.amc21` identity, supports basic local
status/startup assertions and explicit file-only `.als21` opening through the guarded lifecycle
pipeline. Cold adoption has null ALS provenance and no worker ownership; known same-ALS reuse
requires continuous owner identity. Conditional local `context` includes descriptive capabilities;
mode remains unknown, remote identity null and active connection unknown.
Worker-owned local sources block a different open even when clean; borrowed sources require
proved preservation. No generic session close or automatic terminal cleanup is added.

Content reads (`browse_project_tree`, `plc_read`, `network_read`,
`read_cross_references`, `hmi_read`) work on local sessions. Read handlers use the worker's
`WithEngineeringRoot` (`ProjectBase`).
`ProjectCapabilityCatalog.OperationFor` is the only worker-method→capability map for both host
and worker gates; a new worker method must map through it.

Local sessions also support `plc_write`, `network_write`, `compile_check` and `save_project`.
Content handlers, write and compile included, use `WithEngineeringRoot`, or `WithActiveContext`
when native access or transactions also need the Portal handle. Content services take `ProjectBase`;
capability gates determine eligible container kinds. A local
`save_project` calls `LocalSession.Save()` with the identity re-check adjacent to the save; it
never updates from or checks in to the Project Server, and read-write confirmation says so.
Create, save-as, archive and close stay standalone-only.

## Write safety model

Access tiers are capability presets in the shared `OperationPolicyCatalog`, enforced at discovery,
host dispatch before worker activity, and worker dispatch before Siemens calls. Unknown operations
are denied in every mode. `SessionSelection` is permitted in every mode: `bind_project` adopts or
switches to an already-open project without opening, creating, saving or closing. Ordinary reads
never bind or switch. Content tools take no `projectPath`: with no verified binding (a configured `--project` is grounded by status first) they return `binding_conflict` and the caller must `bind_project` first; a retired `projectPath` is a canonical `validation_error`. Only `open_project`, `create_project` and `retrieve_project` open a project; there are no implicit
opens. Worker ownership does not survive detach. Read-only never opens, creates, saves or closes.
The access mode is resolved once at startup (`Cli/AccessModeParser`, also used by `DoctorCliParser`): CLI (`--access-mode`, `--read-only`, `--read-write`) > `TIA_MCP_ACCESS_MODE` > `accessMode` in the owner's server settings file `%APPDATA%\TiaMcpServer\settings.json` (or `TIA_MCP_SETTINGS`; Contracts `ServerSettingsFile`, closed schema version 1, an invalid, unreadable or variable-named missing file refuses startup even when CLI or environment decides) > default read-write; the source (`cli`/`environment`/`settingsFile`/`default`) and the file are logged at startup and reported by doctor (`accessModeSource`, `settingsFile`). Only the password manager writes the file (owner request 2026-11-02: choose the mode in the program, not in `claude_desktop_config.json`); the server process never writes it and no MCP tool reads or changes it.
Lifecycle, download, online-write, online-connection and upload confirmation follow access mode. `plc_write`, `network_write`, `hmi_write` and `vci_write` use guarded writes with no server elicitation, except `plc_write` calls with fail-safe items (below); no tool uses safety tokens.

Lifecycle, Network, PLC, HMI, VCI, library writes, `plc_download`, `plc_online_write`, `plc_tia_online` and `plc_station_upload` use the guarded single-call pipeline. Lifecycle, `plc_download`, `plc_online_write`, `plc_tia_online` and `plc_station_upload` confirm every
actual read-write call; Network, HMI and VCI have `ConfirmsEveryCall=false`, no acknowledge guards, and
zero server elicitation in read-write, full, or dry runs; PLC is the same except that a call with a fail-safe item confirms (see Fail-safe PLCs below). The generic batch tools
(`preview_write_batch`/`apply_write_batch`), safety tokens, the token core and the legacy write audit
stream were removed.

- **PLC writes**: `plc_write(operations, dryRun=false)` executes by default; set `dryRun:true` for preview. Same binding, ordering, 50-item, stop-at-first-failure and no-rollback rules as Network; the 202 operations are listed in the tool description (`move_tag` is a guarded create-under-a-temporary-name, delete, rename; an `IsSafety=true` tag moves under the safety login rule, the same table is refused and copies the multilingual comment per language). The granular block edits (not live-tested) are `PlcBlockEditMethods` in Contracts: interface member edits are planned host-side on the exported SimaticML with the Siemens-free model in `Contracts/Plc/Interface` and imported through the existing `update_block_logic`/`update_type_content` worker path with the export's hash; `update_db_member`, `create_instance_db`, `rename_block`, `renumber_block`, `copy_block`, `move_block` and `move_tag_table` are worker methods taking `WorkerRequest.PlcBlockEdit`, gated as `plc_write` (reads `get_block_interface`, `get_type_interface`, `get_db_values` as `plc_read`) by `ProjectCapabilityCatalog.OperationFor`; they verify by re-reading (`interfaceMember`, `dbMember`, `block`, `tagTable`) and refuse know-how-protected blocks for round trips (their export carries only the interface; fail-safe blocks follow the safety login rule below). `copy_block`, `move_block`, `move_tag_table` and `move_tag` run their steps in one `ExclusiveAccess` transaction (`Openness/Plc/PlcRoundTrip.cs`, `WithActiveContext`); a failed move whose rollback did not restore the original re-imports it, then keeps its export in `%LOCALAPPDATA%\TiaMcpServer\recovery\<UTC>-<guid>\` (`PlcRecoveryStore`), and returns `PlcBlockEditFailureInfo` as the failed item's `result` through the `WorkerResponse.PlcDownloadOutcome` evidence channel. The `contentDiff` effect compares like with like (`PlcContentDiff.BuildForWrite`, K31): a plain SimaticML document in format xml is diffed against the export bundle's `.xml` document only (`currentDocument`). Compiler messages (`CompileReportProjection.Flatten`, K04) drop TIA Portal's blank container rows and carry their paths as a `/` chain (`Contracts/Block/CompileMessagePaths`); the import compile report in `blockImportOutcome` keeps TIA Portal's texts within `BlockImportOutcomeLimits` (errors, then warnings, then information). Content writes pass `content` plus `expectedContentHash` from a `plc_read` in the same format; stale content is `state_changed`, and content over the value budget (60,000 characters by default, raised with `--max-item-chars`) has no hash and cannot be written. Write contract `2.0` (`plc_read` stays `1.0`): creates are not pre-checked for collisions (except technology objects and their groups, whose existing names the planner and the worker refuse); scoped live cases cover duplicate tags/tables/blocks/groups, the default-table delete and the four namespace directions in the acceptance report. Other collision directions are unverified. A native `EngineeringTargetInvocationException` in a mutation worker method fails `engineering_rejected` with `engineeringError` (see Failure categories below). Guards are block (`plc_ob_singleton_exists`, kept because Portal's own rejection was never reachable through the tool and TIA Portal allows one OB per singleton class; `plc_safety_login_required`) or info (`plc_state_unverifiable`, info since 2026-11-01 (owner decision: never stricter than TIA Portal; the item runs and TIA Portal decides), for incomplete inventory, unreadable update/delete targets, delete consequences or constant values, and unexportable content; `plc_deletes_block`, `plc_deletes_group_contents`, `plc_deletes_table_contents`, `plc_address_overlap`, `plc_move_tag_recreates`, `plc_deletes_watch_table`, `plc_changes_interface`, `plc_block_round_trip`, `plc_moves_tag_table`, `plc_generates_from_source`, `plc_deletes_external_source`, `plc_renames_group`, `plc_export_overwrites_files`, and the V21 pitfall guards `plc_s7dcl_import_may_alter`, `plc_textual_interface_overwrite_may_terminate`, `plc_save_before_write_recommended` for behaviour reported by rickgaiser/TiaMcp and not verified on V21; the worker counts block exports per binding in `BlockExportLedger`, read by the planning-only worker method `get_block_export_state`, and a SIMATIC SD import with findings gets an `s7dclConstructs` verification entry; see [V21 pitfalls](docs/SupportedOperations/V21_PITFALLS.md)). Update and delete targets still pre-flight `target_not_found` (any planning refusal rejects the whole call before its first item; a multi-item call's message says no item ran, K25); a create into a missing parent group or folder fails at mutation. Later items may depend on objects created earlier in the call (`dependsOn`, replanned before their mutation); a granular edit left without a planned document (e.g. its replan found no SimaticML because TIA Portal does not export a block not compiled since it was created, K55) fails `worker_operation_failed` with the planning reason, is not sent and gets no verification entry; a failure the host produced before anything was sent (`WorkerDispatchState.NotSent`, `WriteRun.ProvablyNotSent`, K60) carries the "stopped before it was changed; earlier operations stay applied" warning (none when no earlier item was sent), never "may already have changed". A failed item's read-back entry is never success true in any write tool (K58, `TrustedWriteVerifier.NeverVerifiedWhenFailed`: it reports the state read afterwards), and a failed later item never makes a superseded entry "verified there". Verification: `trusted` for completed non-content items without a read-back, `tag` (create/delete/move_tag and a commented update_tag re-read through `list_tag_tables`/`read_tag_comments`; `create_tag`/`update_tag` take `comment`+`commentCulture`, set through `LanguageSettings.Languages` → `Comment.Items.Find` → `Text`, K22), `block` for `delete_block` (gone; it owns the PLC-wide block-name key, so a later same-name create in any group supersedes it), `block` for `create_block` from the worker's re-resolve of the created block by its path (K57; no host read, the new block is not compiled), `readBack` for a `set_plc_access_level` whose worker read-back matched (K24) and for the four safety access writes from the worker's `loggedOnAfter`/`passwordSetAfter` (K49), `file` for `export_opcua_xml`/`export_tag_table` from the worker's re-hash of the placed file (K50), `unverifiable` (success true) for a write whose worker read-back matched but whose host re-read TIA Portal refused for an inconsistent object (K01/K20: the worker's `ExportConsistencyEvidence` appends a `PlcExportConsistency` hint naming `compile_check` when an export throws and `PlcBlock.IsConsistent` reads false; never compiles), `contentHash` (a re-export, equal to the next `plc_read` hash and usable as the next `expectedContentHash`, never computable from the content) for content updates, `superseded` for overwritten items (`export_technology_object`, `export_tag_table` and `export_opcua_xml` own only the key of the file they write, like the other exports, so an export never supersedes an item on the exported object and is superseded only by a later write of the same file, K59, `PlcVerificationPolicy.SideFileExports`; a short-path `update_block_logic` is conservatively superseded by a later same-name block item or any group delete on that PLC; interface edits and `update_db_member` supersede per member since 2026-11-02 (K03, `PlcVerificationPolicy.MemberScoped`): member keys below the block/type key, a whole-content key a later interface edit offers and whole-object items own, so an edit of another member keeps its own read-back); a failed non-content item has no verification entry, so inspect it with `plc_read`. `update_tag` applies a rename first and reads `Name` back, because Portal silently ignores a colliding rename: the item fails `postcondition_failed` before any other property changes. Audit confirmation is `none` in read-write and `policy` in full.

`TiaMcpServer/OperationBatches/StructuredOperationBatch*.cs`. These rules bind every tool on it
and any future tool that migrates onto it:

- **Reuse the shared gate.** A new structured tool builds on `StructuredToolResult` /
  `StructuredOperationBatch`; do not hand-roll a parallel canonical-JSON mechanism for a new
  domain. `CanonicalWriteSafety` and the generic-batch token infrastructure are retired.
- **Text and structured documents are the same document.** A migrated tool's `content` text block
  and its `structuredContent` come from exactly one `CanonicalJson.Serialize` call. They must
  never be built from two independent renderings that could drift apart.
- **Worker success payloads are typed.** A migrated tool declares exactly one CLR result type per
  operation (see `TiaMcpServer/Network/NetworkPayloadContract.cs` for the pattern) and rejects a
  payload that does not decode as that type — category `protocol_error` — rather than forwarding
  worker-shaped data under a schema that does not describe it. The rejected payload is never
  echoed back.
- **Required members are enforced by the reader.** A host decode of a worker payload whose root
  writes explicit nulls goes through the worker-payload reader
  (`CanonicalJson.DeserializeWorkerPayload` / `NormalizeWorkerPayload`). Every member is required
  unless it is declared conditional with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]`.
  A new conditional member is added to `ConditionalMemberRegisterTests`, with a description stating
  when it appears. Do not hand-write required-member lists.
- **No nested JSON strings.** A migrated tool's operation results are real JSON objects/arrays
  under the response document, never an escaped JSON string a caller has to parse a second time.
- **Every tool is structured or registered as legacy.**
  `TiaMcpServer.Tests/Tools/ToolOutputContractConformanceTests.cs` fails when a tool is neither
  on this contract nor listed in its legacy register with a reason. When a tool migrates, remove it
  from that register and add a success probe and a rejection probe. The target envelope and
  migration order are in `docs/roadmap/json-contract.md`.

See `docs/ARCHITECTURE.md` §7a for the full seam description and the exact host-to-worker
selector boundary, and `docs/SupportedOperations/NETWORK_OPERATIONS_SUMMARY.md` for the concrete
Network contract these rules describe in the abstract.

## Plans, specs and evidence (lifecycle)

These rules override the default output locations of the superpowers skills (brainstorming: "Write the validated design (spec) to"; writing-plans: "Save plans to") and of any similar tool.

- Specs go to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, plans to `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`, run evidence to `docs/superpowers/evidence/YYYY-MM-DD-<topic>/`. These three directories are a transient per-PR working area: collapsed in diffs and empty on `main`.
- Never link a transient file from outside `docs/superpowers/`; cite it as "PR #N, commit `<sha>`".
- Before pushing documentation changes, run `python -I scripts/verify-docs.py --archive-tag docs-archive-2026-10-30` (`python3` on Linux/macOS).
- Before the PR merges, delete everything you added there in a final commit (`docs: prune working files`). First move what must survive: a lasting decision to `docs/adr/` (one ADR, see its README), behavior to `docs/ARCHITECTURE.md` or `docs/SupportedOperations/`, follow-ups to `docs/IMPROVEMENT_LOG.md`, the live-verification report to `docs/superpowers/acceptance/reports/`, and verified raw Openness call/response files to `docs/superpowers/acceptance/reports/inputs/` (listed in its `README.md`). MCP-level traces, preflights, restoration dumps and timing outputs are not kept; use `scripts/timing/` for measurements.

## Documentation layout

`docs/` is grouped by audience, not by document type:

| Path | Audience |
| --- | --- |
| `docs/guides/` | people **using** the server — installation, client configuration, troubleshooting |
| `docs/development/` | people **building** the server — building, MCP sandbox testing, packaging |
| `docs/roadmap/` | direction — per-area tactical roadmaps (root `ROADMAP.md` is strategic) |
| `docs/SupportedOperations/` | per-area operation reference |
| `docs/ARCHITECTURE.md` | the design; keep current per its own §11 |
| `docs/IMPROVEMENT_LOG.md` | engineering log — open follow-ups first, completed work at the end |
| `docs/adr/` | architecture decision records — why the design is as it is; project history |
| `docs/superpowers/` | live-verification reports under `acceptance/reports/`; transient working area for plans, specs, evidence (empty on `main`) |

Two rules that keep this from re-rotting:

- **A new document under `docs/` is not complete until it is reachable from `docs/README.md`**,
  directly or through the index of its directory. An unreachable document is unfindable in practice.
- **`README.md` is also the NuGet package readme**, declared via `<PackageReadmeFile>` in
  `TiaMcpServer/TiaMcpServer.csproj`. Relative links do not resolve on nuget.org, so every
  cross-document link in `README.md` and `README.de.md` must be an absolute URL pointing to the public fork
  `https://github.com/Birger90/tia-portal-mcp-server/blob/main/...`, because many linked documents
  exist only in the fork. Every other document uses relative links.
- **Documentation is bilingual (owner decision, 2026-11-02)**: `X.md` English, `X.de.md` German, same directory, a
  language switch line under the first heading of each (`**Language:** English · [Deutsch](X.de.md)` /
  `**Sprache:** [English](X.md) · Deutsch`). The bilingual set is the root documents, `docs/README.md`,
  `docs/FORK_FEATURES.md` and every `*.md` directly in `docs/guides/` and `docs/SupportedOperations/`; a change to one
  of them changes both versions in the same commit, and `scripts/verify-docs.py --bilingual` (CI) refuses a missing or unlinked pair.
  German links without an anchor go to the `.de.md` of a set document; links with an anchor keep the English file.
  Use Siemens' German TIA terms (Baustein, Variablentabelle, übersetzen, F-Ablaufgruppe, ...). ADRs, acceptance reports
  and roadmap notes are still English only and are translated next.

`README.md` is a landing page: pitch, tool list, write-safety model, architecture summary, quick
start, and the documentation map. Procedure belongs in `docs/`, not in the README.
